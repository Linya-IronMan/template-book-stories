# Git Commit 规范

## 1. 目的

本仓库所有提交信息都必须遵守本文档。

## 2. 标题格式

提交标题统一使用以下格式：

```text
<type>: <中文描述>
```

若本次改动仅影响单个子包，则提交标题必须改为：

```text
<type>(<子项目包名>): <中文描述>
```

约束如下：

- `type` 必须使用小写英文。
- `type` 后必须紧跟英文冒号与一个空格。
- `scope` 仅在改动范围明确落在单个子包时使用。
- `scope` 必须填写真实子项目包名，不允许自定义缩写。
- 描述应以简体中文为主；涉及稳定模块名、技术名词或历史沿用短语时，可保留必要英文。
- 提交标题应直接说明本次变更的核心意图，避免空泛描述。

正确示例：

```text
feat: 修复单元测试
feat(core): 优化 selection mask 缓存命中
fix(server): 修复本地服务鉴权时序问题
perf(three): 优化拖拽相机卡顿问题
fix: 修复worker导致的时序错位
perf: cache visible selection refs
chore: 用 vendored 方式解决 cargo check
```

错误示例：

```text
Feat: 修复单元测试
fix 修复时序问题
feat(point): 优化缓存
feat(core server): 同时修改两个包
update: 改了一些东西
feat: update code
```

## 3. 允许的类型

根据当前仓库已有提交记录，优先使用以下类型：

- `feat`：新增功能，或对现有功能做可感知增强。
- `fix`：修复缺陷、错误行为、时序问题、兼容性问题。
- `perf`：性能优化、缓存优化、减少计算或渲染开销。
- `chore`：工程维护、依赖处理、构建或开发环境调整。

若变更不属于以上类型，应优先重新判断其真实意图，避免随意扩展新的 `type`。

## 4. 子包 Scope 规则

当前仓库子项目包名如下：

- `core`
- `server`
- `three`

使用规则如下：

- 仅修改 `packages/core` 时，必须使用 `feat(core): ...`、`fix(core): ...` 这类格式。
- 仅修改 `packages/server` 时，必须使用 `feat(server): ...`、`fix(server): ...` 这类格式。
- 仅修改 `packages/three` 时，必须使用 `feat(three): ...`、`perf(three): ...` 这类格式。
- 若改动分别落在多个子包，且可以拆分，应拆成多个 Commit，每个 Commit 只对应一个子包。
- 禁止使用 `feat(core server): ...`、`fix(core,server): ...` 这类多 `scope` 写法。
- 若同时修改多个子包，但该变更属于不可拆分的联动改动，则不要使用 `scope`，直接使用 `<type>: <中文描述>`。
- 若同时修改根目录与子包，也不要使用 `scope`，直接使用 `<type>: <中文描述>`。
- `scope` 只允许写一个包名，不允许在一个提交里写多个包名。

示例：

```text
feat(core): 优化连接管理器重连逻辑
fix(server): 修复 subjects 接口返回状态错误
perf(three): 降低渲染阶段的无效刷新
feat: 调整 core 与 server 的跨包联动数据流
feat: 调整跨包联动的 selection 数据流
chore: 更新仓库级构建配置
```

## 5. 描述要求

提交描述必须遵守以下要求：

- 使用简体中文描述本次变更的直接结果。
- 若描述中包含固定模块名、接口名、技术术语，可直接保留英文，不强制翻译。
- 尽量聚焦单一主题，避免把多个不相关改动放进同一个提交。
- 不写“更新代码”“修改内容”“调整一下”这类低信息量表述。
- 若为连续优化，可在描述末尾追加序号，但仍需保持语义完整。

推荐写法：

- `feat: 优化本地 LOD 可见性查询实现`
- `feat: 优化拖拽相机卡顿问题 4`
- `feat: 添加渲染日志`
- `fix: 报错问题`
- `perf: cache select settings in memory`

不推荐写法：

- `feat: 改动`
- `fix: 修一下`
- `chore: 调整`
- `feat: stuff`

## 6. 一次提交只做一件事

每个 Commit 应尽量只表达一个独立目的：

- 一个功能点对应一个 `feat` 提交。
- 一个缺陷修复对应一个 `fix` 提交。
- 一个性能优化主题对应一个 `perf` 提交。
- 一个工程性维护动作对应一个 `chore` 提交。

若一次改动同时包含多个独立目标，应拆分为多个提交，避免后续回滚、排查和生成变更日志时难以定位。

若改动落在多个子包，但本质上可以拆开提交，也必须拆分，不允许通过多 `scope` 混在一个 Commit 里。

## 7. 提交前检查

提交前至少自检以下内容：

1. 提交标题是否符合 `<type>: <中文描述>`。
2. 若只修改了一个子包，是否已改为 `<type>(子项目包名): <中文描述>`。
3. 若修改了多个子包，是否已经优先拆分为多个 Commit，而不是写多 `scope`。
4. `type` 是否准确表达本次改动目的。
5. 描述是否足够具体，且与实际改动一致。
6. 是否把不相关改动混入同一个 Commit。
